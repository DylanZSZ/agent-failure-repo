# Contribute task-design reference sessions

Updated 2026-10-24. The default contribution is a local collection of real conversations useful for designing agent failure tasks. Start with the short message in README.md. Sources from both Claude Code and Codex may be inspected within the project and history scope the user authorized.

## What to collect

Select a session when it contains a real task and observed agent action, a concrete design use, and locatable original evidence. State what natural task could be built, what state change or handoff matters, and what behavior could be observed. A successful delivery or normal repair can be a useful comparison when this use is specific.

Group related source files by actual task and retain their full available local originals or verifiable archive references. Mark a lead needs evidence when its decisive action cannot be found in the original record. Give a one-sentence reason for reviewed sessions that are not selected. Unread material remains unread; it is not a negative result.

Work in stated batches. Inventory the authorized histories, browse task starts and visible actions, verify the relevant original calls and results, then write the private session list and a short REPORT.md. Record source IDs, anchors, read and unread ranges, and material gaps. See AGENTS.md for the working rules and commands/README.md for the reader.

## Improve the selection workflow

Change the workflow only for a concrete missed or weak selection, missing key material, or repeated work that delays collection. A full first acceptance check or a change to selection should compare its decisions with an independent review of a frozen pool that includes unselected sessions. A format fix uses a targeted check. Record what changed and whether it helped, then return to collection.

For proposed long-horizon tasks, link templates/task-candidate.md from the session list. Assess state dependencies separately from observed behavior and record carrier reuse, adaptation, or new construction. Independent validation uses a frozen manifest without expected labels; material used to revise rules is a development replay. See current AGENTS.md for the complete contract.

## Later task packaging and sharing

The older guides in docs/LONG_HORIZON.md, docs/EVIDENCE.md, docs/REPRODUCING.md, and docs/SUBMITTING.md apply when a user separately asks to explain a specific failure, create a runnable task, or prepare a public submission. The problem scaffolder and validator still support that work. They are not collection admission rules.

Keep raw histories and private notes in .local or another authorized private location. Review exact sanitized files with the owner before upload or publication. Inspecting a project history does not authorize paid model calls or sharing its raw contents.
